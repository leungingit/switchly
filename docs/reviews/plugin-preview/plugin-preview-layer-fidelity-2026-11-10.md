# 分层捕获的保真度、裁剪遮挡与动画一致性实验

日期：2026-11-10。接续 [第三轮捕获实验](plugin-preview-view-capture-2026-11-10.md)。用户明确要求先验证，不接入正式工具。

## BG-D12：建立原生窗口参考，简单末层叠加不能处理裁剪和遮挡

本轮沿用真实共享 `PluginSlotSurface`、`PluginOverlayView`、`PluginScene3DPointerView`、真实外仓音乐插件与原 GLB；只注入合成媒体 fixture。按 `project.yml` 直接编译 98 个既有 Swift 源文件，加一个系统临时目录中的实验助手；仅替换临时入口，不修改仓库 Swift、构建配置、公开契约或正式工具。复用现有预览 worker 和资源。最终候选 `compile_exit=0`，三次完整运行均 `exit=0`，实际通过报告和图片判定，不仅检查退出码。

实验壳为 300×516pt。静态参考窗口位于屏幕内，设置 accessory、borderless，窗口层级为 `CGWindowLevelForKey(.desktopWindow)-1`，实际 `level=-2147483624`，只 `orderBack`，不激活、不 makeKey。只用 `/usr/sbin/screencapture -x -o -l <实验窗口编号>` 捕获候选自身窗口，不抓取用户桌面或其他应用。此处只作为原生 WindowServer 参考，不能拿它声称完全屏幕外捕获成功。

随后将同一窗口移至 `(-10000,-10000,300,516)`，核对所有 `NSScreen.frame` 均不相交，再用分层路线捕获。所有静态组记录 `offscreenOverlap=false active=false key=false`。第一轮 6 组，补充轮和最终轮各 8 组；后两轮每组各取连续两次原生参考图，16 对参考图的规范化像素差均为 0。

比较两种仅存在于临时候选中的方法：

1. **最后叠加**：先缓存整棵原生视图，再将真实 `SCNView.snapshot()` 按视图转换后的区域绘制在最上层；就是上一轮的简单方法。
2. **原层级替换**：先取同一真实 SCNView 的快照；在它的原父视图、原 frame 和同级位置临时插入 NSImageView，隐藏原 SCNView，再缓存整棵原生视图；随后立即移除替身并恢复原视图。试图让已有树处理父级裁剪和前景层级。此方法会临时修改呈现树，不等于通用、无副作用的产品方案。

实验边界配置：

- 圆角：220×390pt 的父容器位于 `(40,55)`，子内容偏移 `(-40,-55)`，父层 `masksToBounds=true`、圆角 70pt。
- 不透明／半透明遮挡：原生前景矩形位于 `(50,200,200,80)`，分别为红色不透明和青色 alpha=0.55，均含文字。
- 原生玻璃：`NSVisualEffectView` 位于 `(40,190,220,100)`，`.hudWindow`、`.withinWindow`、`.active`，圆角 18pt。本轮不测试 `.behindWindow` 或采样真实桌面背景。
- 纯 2D 对照隐藏 SceneKit 表面，保留相同壳和前景，以检查差异是否只由 3D 拼接引起。布局壳与这些边界为实验构造，不冒充插件已公开支持的全部布局。

## BG-D13：原层级替换改善几何保真，玻璃仍失败

以下为最终轮输出，所有图 `600×1032`。先将图像归一化到 8-bit sRGB RGBA，比较 RGB；“差异像素”定义为某一 RGB 通道绝对差 >8，占整幅图的比例。MAE 为 RGB 每通道绝对差均值，范围 0～255。阈值 8 仅用于描述误差分布，**不是新设的正式验收阈值**；两个方法都未取得普遍像素完全一致。

| 场景 | 最后叠加：差异像素占比 | 原层级替换：差异像素占比 | 替换后 MAE |
| --- | ---: | ---: | ---: |
| 普通深色 | 0.01066% | 0.01066% | 0.00850 |
| 普通浅色 | 0.01066% | 0.01066% | 0.00540 |
| 父级圆角裁剪 | 18.30669% | 0.03924% | 0.01379 |
| 不透明前景 | 10.34658% | 0.01066% | 0.05868 |
| 55% 半透明前景 | 10.34658% | 0.01066% | 0.06694 |
| 原生玻璃前景 | 13.73224% | 6.80443% | 1.09893 |
| 纯 2D 半透明对照 | 0.00953% | 0.00953% | 0.05122 |
| 纯 2D 玻璃对照 | 14.02245% | 14.02245% | 0.83785 |

主控实际查看了六场景的原生参考／最后叠加／原层级替换并排图，以及最终轮的圆角、普通与遮挡差异图，确认：

- 最后叠加把原本应被父级裁掉的 iPod 部分重新画出来，也将前景矩形盖掉。不能据上一轮无遮挡布局可用，推出通用布局可用。
- 原层级替换保留本例圆角、父级裁剪和不透明遮挡。最终轮普通组仍有 66 个像素的通道差 >8，裁剪组为 243 个；差异图显示圆角边缘、局部文字／控件和轮廓存在残差。结论是几何关系改善，不是与原生逐像素一致。
- 玻璃参考图会对后方轮盘形成模糊／材质覆盖；替换图仍能清楚看到爱心和轮盘，视觉效果明显不同。纯 2D 玻璃对照同样出现可见的材质明暗差异和 14.02245% 的差异像素，因此不能把失败仅归因于插入 3D 快照。
- 半透明有跨轮不稳定：第一轮原层级替换差异为 **10.07235%**，补充及最终轮为 **0.01066%**。参考窗口位置第一轮为 `(2162,178)`，后两轮为 `(526,181)`；实验跟随 `NSScreen.main`，未锁定显示器 ID 和颜色配置。没有足够证据将变化归因于显示器、颜色空间或某一个系统合成细节。不能只选择后两轮较好结果宣称半透明普遍通过。

最后叠加的圆角失败在三轮均复现（差异约 18.31%～18.54%）；玻璃在三轮原层级替换中仍失败（约 6.38%～7.60%），不是一次偶然 PNG 错误。未覆盖视图旋转／缩放 transform、任意 mask、多 SCNView、混合 SwiftUI clipping、HDR／广色域或跨显示器固定配置矩阵。

## BG-D14：真实产品的爱心前景也会被最后叠加吞掉

最终轮在真实 iPod 视口的已知 top-left 坐标 `(150,276)` 换算窗口坐标，向该窗口分派原生 mouse-down／mouse-up，实际输出 `ACTION love`。动作经过现有共享视图与 worker，会话更新合成媒体的收藏状态；没有直接调用 `handleAction` 或 JS action 来代替输入。

产品已有 SwiftUI `loveBurst` 会在模型前景显示粉色爱心，包含缩放、透明度与阴影。实验在同一主线程执行段依次采集 2D 缓存、SceneKit 快照和原层级替换图，观察四个相位。下表在固定的图片区域（x=230..<370、y=330..<490 px）统计粉色像素，判定为 R>130、R>G+55、R>B+35；点击前该区域统计为 0。

| 目标相位 ms | 三种采集完成时的实际耗时 ms | 缓存粉色像素 | 最后叠加 | 原层级替换 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 189.7 | 1444 | 0 | 1464 |
| 250 | 319.0 | 2461 | 0 | 2497 |
| 450 | 523.8 | 2282 | 0 | 2306 |
| 700 | 782.9 | 0 | 0 | 0 |

主控实际查看目标 250ms 组：缓存只有背景、爱心与底部实验标注；最后叠加有 iPod 却没有爱心；原层级替换同时保留 iPod 和前景爱心及阴影。查看目标 700ms 组确认爱心已消失。**这是产品真实 SwiftUI 前景遮挡的证据，不只依赖人工矩形。**

实际完成时刻明显晚于目标相位，目标相位不可写成精确捕获时间。缓存和替换图的粉色像素数也不相同；本轮没有将差异唯一归因于动画推进、插入替身或采样，不把“都保留爱心”升级为同帧像素一致。

## BG-D15：跨等待采集会错帧，同一主线程段只锁住一类时钟

使用共享 `PluginScene3DController.spin(.right)` 与既有 60Hz `PluginScene3DFrameTimer`，真实相机旋转，不是自造旋转模型。实验 2D 标注在缓存时读取 `cameraPose.yaw`；再记录 SceneKit 快照前的相机 yaw。每种策略每轮 20 个样本，三轮重复。

| 采集策略 | 最终轮状态不一致 | 三轮合计 | 最终轮最大圆周角差 | 最终轮两层采集耗时 |
| --- | ---: | ---: | ---: | --- |
| 两层之间异步等待 20ms | 20/20 | 60/60 | 15.68783° | 26.92～37.89ms |
| 同一主线程执行段，不 await | 0/20 | 0/60 | 0° | 5.45～11.47ms |
| 等旋转完成后采集 | 0/20 | 0/60 | 0° | 5.87～16.18ms |

角差按 `min(abs(a-b),360-abs(a-b))` 计算。补充轮曾记录直接相减的 345.79°，这是 ±180° 归一化边界，不能当成真实转过 345.79°；换算后的该轮最大实际角差为 14.20605°。第一轮最大为 15.82890°。

**可以确认**：跨异步等待采集会组合不同的相机状态；无 await 能阻止当前基于主 RunLoop Timer 的相机在两层之间被推进；等待此相机旋转完成也能避免本例状态差异。

**尚不能确认**：所有 SwiftUI／Core Animation／SceneKit 画面严格来自同一个 GPU 呈现帧。`cameraPose` 相同只是模型状态证据；2D 缓存、SceneKit 快照和原层级重采集仍是顺序调用。产品还存在 SwiftUI 爱心和跑马灯、DispatchQueue 延迟、SceneKit 按压动画等独立时间链。静态时钟 `pluginSceneNow` 只覆盖已有 2D scene 的时间消费，不会自动冻结这些动画。

另附加了 SceneKit 自主 SCNAction 的诊断探针，但记录的 presentation 角度全为 0、未取得实际推进，因此该组不具备检验独立渲染时钟的前提。**不将其 0/20 变化当成动画同帧通过证据**。严格同帧仍未通过，需后续验证可控呈现时间、事务边界及状态恢复，而不是以移除 await 或固定 sleep 宣称解决。
