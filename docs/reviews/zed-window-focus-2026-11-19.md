# Zed Dock 窗口切换排查

## ZED-D01 旧运行实例与当前构建对照

- 现场为 macOS 27.2.1、Zed 1.29.2。15:42 的 Switchly 日志显示，Dock 预览匹配到两个 Zed 窗口。点击窗口 `10067` 后，Zed 已成为前台应用，读取 `AXWindows` 仍连续返回 `-25211`，候选数为 0，未执行窗口提升。
- `ps` 显示旧 Switchly 进程 `20343` 于 11 月 17 日 13:59 启动。用 `lsof -d txt` 和 `stat -f %i` 对照，它实际映射的二进制 inode 是 `187816791`，同路径磁盘文件为 `187847027`。Zed 运行进程的二进制 inode 与磁盘一致。此次对照确认了 Switchly 旧实例与磁盘构建不一致，尚无法单独证明该差异引发 AX 错误。
- 用当前源码编译临时独立探针，直接调用 `AccessibilityService.resolveAndFocus`，在同一桌面的两个现有 Zed 窗口之间交替切换 4 次。每次都返回成功，Zed 前台 PID、AX 焦点 ID 与 CG 顶层窗口 ID 一致。独立探针与正式应用各有自己的 AX 调用环境。
- `codesign --verify --deep --strict` 验证磁盘上的 Debug App 通过。仅重启 Switchly，新进程 `82188` 映射 inode `187847027`，版本为 `1.4.1`。启动日志确认辅助功能与屏幕录制权限均已授予。未重启 Zed 或更改权限。
- 待验证：从重启后的正式 Dock 预览点击原先失败的窗口，检查对应日志中的候选数量与精确焦点结果。原生自动化连接 Dock 超时，未取得该入口的点击证据。当前未修改聚焦代码。

## ZED-D02 正式 Dock 复验与跨应用排查

- D01 的正式入口待验项已完成。用户确认恢复后，核对 16:09 至 16:14 的本地日志，共 5 次真实 Dock 点击。窗口 `10064`、`10067` 均通过精确 AX ID 匹配，首次提升即通过 CG 校验。前后的 Zed PID 均为 `85178`。
- 已确认的失败点在 `AXWindows` 读取。旧 Switchly 进程在 11:25 对同一 Zed PID 尝试写入 `AXManualAccessibility` 也直接得到 `-25211`。这次聚焦没有走到 `AXRaise`。同期同一个 Switchly 实例仍能查询和切换 Chrome，说明失败并未影响它的所有 AX 目标。重启 Switchly 并加载当前产物后恢复，底层返回 `-25211` 的触发条件尚未查明。
- 对照扩大到 11 月 12 日至 19 日的本地轮转日志。按窗口 ID 和目标 PID 关联的切换记录中，Zed 有 18 次 `-25211`，其中 7 次记录正式 Dock 失败，其余 11 次只通过延后可见性校验。ego lite、Gemini、Lark Helper、ChatGPT 也出现过该返回码，对应记录均进入延后可见性校验。Gemini 另有一段 `-25204` 通信失败伴随 Dock 切换失败。样本内 Chrome 有 81 次、VS Code 有 8 次通过常规聚焦校验。日志覆盖已发生的操作，不能推断未操作应用的故障率。
- VS Code 在 [跨桌面记录 D10](all-spaces-window-preview.md#d10其他-space-窗口聚焦的实测根因与修复) 的已修场景中可读取 AX 窗口列表，列表只包含当前桌面的窗口，缺少其他桌面的目标 ID。Zed 本次失败时整次列表读取返回错误。优先按失败阶段区分两类故障。
- 受控对照只替换临时探针的可执行文件，确认旧进程仍映射旧 inode。同一旧进程在替换前后连续 12 轮均成功读取 Zed、Chrome 和 Finder 的 `AXWindows`。这说明本实验中 inode 不一致不足以复现故障，不能排除正式 App 的签名或 AX 会话状态。对三个故障／重启窗口筛查系统日志，未找到可归因于 Switchly 的辅助功能拒绝或签名不匹配记录。
- 现场快照中，独立探针对 21 个正在运行的普通应用只读枚举，21 个均返回 `0`。它验证的是探针当时的 AX 访问状态。后续正式回归应分别覆盖同桌面双窗口、跨桌面窗口和启动后运行较久的实例，以点击后的精确窗口 ID 为验收结果。复发时应在重启前对照同一个目标和一个已知正常目标，保留宿主 PID、实际构建身份、`AXWindows` 返回码与精确焦点结果。
