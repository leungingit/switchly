# 桌面九宫格：场景调研、性能判断与功能交互说明

调研日期：2026-10-20。状态：候选功能方案，初稿时未实现、未进行原生 Spaces 实机原型验证。本文基于公开一手资料与当前工作区代码；性能数值中的预算、推算和实验标准均不是实测成绩。

后续进展：[第一轮可行性研究与任务拆分](desktop-grid-feasibility-2026-10-20.md)已完成本机只读桌面探测；读能力取得初步证据，切换、窗口移动、生命周期与完整性能实验仍待验证。以下保留候选产品目标，不代表这些能力已获验收。

最新结论（2026-10-21 整理）：[第二轮受控评估](desktop-grid-evaluation-2026-10-21.md)已取得部分窗口成员变更和生命周期证据，但真实桌面直达尚未通过，完整产品暂不放行。下文的计划是目标说明，不是已完成能力清单。

## 1. 决策建议

建议验证并开发 **Desktop Grid / 桌面网格**：将 macOS 原生桌面以 2×2、2×3 或 3×3 的固定位置呈现，通过总览、方向选择和直接跳转减少寻找桌面的成本。它提供二维导航关系，系统底层仍管理原生 Spaces；不承诺将 Mission Control、系统触控板手势或桌面切换动画改成二维。

需求真实存在，尤其适合 6–9 个长期固定用途桌面的用户，但目前没有代表性数据证明这是大多数 Mac 用户的需求。4 个桌面可受益，未必值得额外学习；单纯追求最快跳转时，系统直达快捷键也必须作为对照。

4–9 个桌面本身不是足以判断性能问题的指标。风险主要来自应用负载、窗口数量和尺寸、多屏及预览刷新。推荐静态结构总览、少量缓存缩略图和按需刷新，不以九路实时桌面视频为默认方案。

最大的前置风险是系统能力与兼容性，而不是九宫格布局。核心导航进入产品开发前必须验证 Spaces 枚举、身份、真实普通/空桌面切换与系统变更后的同步；窗口索引、预览和移动单独设置增强能力门槛，不通过时不得承诺相应能力。完整窗口归属不是纯图标导航的必要条件，但桌面身份和真实切换不能用系统操作指引替代后宣称本功能已交付。

## 2. 是否有真实使用场景

### 2.1 可核查的证据

| 证据 | 说明 | 能证明什么、不能证明什么 |
| --- | --- | --- |
| [TotalSpaces2 官方文档](https://totalspaces.binaryage.com/documentation2)、[网格布局](https://totalspaces.binaryage.com/layout2) | 曾提供二维布局、方向导航、总览、名称与直达快捷键；现已停产，不支持 Apple Silicon | 有成熟产品先例；不能据此断言今天仍兼容或市场规模很大 |
| [AeroSpace 讨论 #1154](https://github.com/nikitabobko/AeroSpace/discussions/1154) | 用户描述需要顺序查看 10 个工作区，查看到最后已忘记前面的内容，希望网格总览 | 有具体、第一人称的定位困难；属于主动发帖样本，存在选择偏差 |
| [AeroSpace 讨论 #2087](https://github.com/nikitabobko/AeroSpace/discussions/2087) | 2026 年用户为工作区总览制作分支，描述方向键选择、回车提交、Esc 取消等行为 | 需求仍在出现且有人主动实现；不能将分支当作官方已发布功能 |
| [TotalSpaces3 官方论坛 alpha 讨论](https://discuss.binaryage.com/t/can-we-help-test-total-spaces-3-if-we-have-apple-silicon/8199) | 2021 年已有 M1 用户使用外屏 2×4 网格，并反馈显示器识别与切换延迟 | 有接近本需求的实际多桌面工作流；历史 alpha 反馈不是现系统性能测试 |

上述证据支持“值得面向重度用户验证”，不支持“所有人需要”或“能量化提高生产力”。

### 2.2 目标场景与适用边界

以下是基于证据归纳的产品假设，尚需用户访谈验证。

| 场景 | 桌面组织方式 | 九宫格的价值 |
| --- | --- | --- |
| 多项目开发 | 每行一个项目，每列开发、查资料、测试 | 用位置记住上下文，同一浏览器不同窗口可分属不同项目 |
| 研究与写作 | 文献、笔记、写作、数据分析、沟通各占一格 | 降低在大量窗口与相似标题中寻找目标的成本 |
| 设计或媒体制作 | 设计、素材、参考、导出监控分开 | 固定位置与名称形成记忆；重负载仍需单独评估 |
| 单屏笔记本办公 | 4–6 个任务上下文 | 弥补可见屏幕有限，减少沿横向逐个查找 |
| 外屏固定工作站 | 每个显示器独立维护桌面集合 | 总览明确显示器归属，避免跳到错误屏幕 |

不优先面向只用 1–3 个桌面、桌面经常随用随删、已熟练使用数字直达，或主要在少数全屏应用间切换的人群。桌面是组织窗口的工具，不是安全隔离环境；不把另一个桌面当作屏幕共享保密保证。

### 2.3 九宫格是否真的更快

用理论按键次数说明潜力，不等同实际耗时：假设任意两个不同桌面间等概率切换、不允许环绕、只执行相邻方向移动。

| 布局 | 最远距离 | 平均最短距离 |
| --- | --- | --- |
| 9 个桌面排成一行 | 8 步 | 约 3.33 步 |
| 3×3 桌面网格 | 4 步 | 2 步 |
| 4 个桌面排成一行 | 3 步 | 约 1.67 步 |
| 2×2 桌面网格 | 2 步 | 约 1.33 步 |

9 桌面时理论方向操作减少约 40%，4 桌面时约 20%。但如果“向下”在底层仍发送三次横向切换事件，系统耗时未必同步减少。数字直达是一次组合键，Mission Control 也可直接点目标；网格更有价值的部分是空间记忆、名称与总览。

建议招募 6–8 名已使用至少 4 个桌面的用户，记录其现有工作流；比较原生横向切换、原生数字直达、网格方向选择和网格点击。测试已知目标跳转、寻找不确定位置的窗口、跨桌面整理，覆盖 4/6/9 桌面。分别记录完成时间中位数/P95、误切率、回退次数与一天后位置记忆。试验性进入标准：6–9 桌面的寻找任务中位耗时改善至少 20%，误切率不增加；这是拟定标准，需要先做基线，不能当作已证实收益。只记录自愿参与的本地测试数据，不新增产品遥测。

## 3. macOS 能力边界

### 3.1 三种实现路径

| 路径 | 实际含义 | 判断 |
| --- | --- | --- |
| 原生 Spaces + 网格导航层 | 真正使用系统桌面，由 Switchly 映射为二维位置 | 推荐验证；保留原生桌面语义，需处理受限接口与兼容性 |
| 自建虚拟工作区 | 将非活动窗口移出可见区域，再恢复位置 | [AeroSpace 官方指南](https://nikitabobko.github.io/AeroSpace/guide#emulation-of-virtual-workspaces)有此实现；涉及恢复、崩溃、多屏与 Mission Control 行为，超出本次定点功能范围 |
| 改造系统桌面管理器 | 改 Mission Control 本身、接管动画或向 Dock 注入 | 不作为 Switchly 默认路线；维护与系统保护成本过高 |

公开 API 可以通知活动 Space 发生变化，例如 [NSWorkspace.activeSpaceDidChangeNotification](https://developer.apple.com/documentation/appkit/nsworkspace/activespacedidchangenotification)，但通知本身不提供完整的 Space 管理能力。[AeroSpace 官方指南](https://nikitabobko.github.io/AeroSpace/guide#emulation-of-virtual-workspaces)也明确指出缺少创建、删除、排序、切换及移动窗口所需的公开 Spaces API。不能把 AX 授权等同于已经获得这些能力。

### 3.2 2026 年的变化：不要沿用过时的 SIP 结论

[yabai 变更记录](https://github.com/asmvik/yabai/blob/master/CHANGELOG.md)记录：7.1.19（2026-04-18）加入 SIP 开启时的 Space 聚焦，7.1.25（2026-05-08）恢复 SIP 开启时的跨 Space 移动窗口。[问题 #2788](https://github.com/asmvik/yabai/issues/2788)提供 macOS 26.4/26.4.1 的验证与私有接口线索。

这说明“不关闭 SIP 就一定不能切换或移动窗口”已经不准确，也不代表 Apple 提供了稳定公开 API。[当前 space_manager.c](https://github.com/asmvik/yabai/blob/master/src/space_manager.c)包含模拟桌面切换手势的回退路径；创建和删除桌面仍走 scripting addition。[SIP 说明](https://github.com/asmvik/yabai/wiki/Disabling-System-Integrity-Protection)仍将 move/swap/create/destroy space 列为需要部分关闭 SIP 的操作。**移动窗口与移动整个 Space 是不同能力。**

以具体 macOS 构建号、芯片架构和实现路径验证，不把上游某版本成功推广到 macOS 12+ 全范围。若参考上游代码，先核许可证与依赖成本；本方案不决定引入 yabai 运行依赖或复制其实现。

### 3.3 功能能力矩阵

| 能力 | 首版建议 | 边界与失败回退 |
| --- | --- | --- |
| 网格布局、位置编号、本地别名 | 计划内 | 是 Switchly 自己的展示，不修改系统桌面名称 |
| 枚举桌面身份与当前桌面 | 核心导航原型前置门槛 | 需验证准确性，并与实际显示场景核对，不能只看 getter |
| 完整窗口归属 | 预览与窗口整理增强能力门槛 | 不能从普通屏幕窗口列表推断完整归属；未知时不显示猜测的窗口数量或预览 |
| 切换到已有桌面（包括空桌面） | 计划内，但以原型成功为前提 | 可评估系统已配置快捷键或受限后端；配置失效时明确提示，不伪报成功 |
| 创建/删除原生桌面 | 首版系统引导 | 用户在 Mission Control 完成，回到 Switchly 再同步；自动创建不是首版承诺 |
| 拖动窗口到格子 | 后端按系统验证后开放 | 不支持时解释并引导系统拖动；不能仅在模型里修改归属 |
| 将应用现有窗口批量移动 | 第二阶段 | 多窗口批操作可能部分成功，不是原子操作 |
| 新窗口自动分配 | 第二阶段 | 与“一次移动”分开；优先解释系统 Dock 分配，并处理冲突 |
| 九格实时视频、系统垂直滑动、系统动画接管 | 不列入首版 | 非活动桌面不能保证实时截图，保持系统手势行为 |

若连桌面身份与空桌面切换也无法可靠验证，只能交付“桌面快捷入口”辅助工具，不能把它当作本方案已实现。

## 4. 4–9 个桌面的性能判断

### 4.1 分开看三层成本

1. **系统桌面层**：不是每增加一个桌面就复制一套 macOS 或全部应用。空桌面数量不是主要资源指标，但桌面管理、背景和合成仍有成本，不承诺零开销。[Apple 的多空间说明](https://support.apple.com/guide/mac-help/work-in-multiple-spaces-mh14112/mac)允许创建多个桌面；支持数量本身不是性能保证。
2. **应用与窗口层**：IDE 索引、编译、视频、浏览器和虚拟机等负载不会因为放在另一个桌面就自动暂停。Apple 的 [App Nap 文档](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html)说明后台节流有条件，音频、后台任务等会影响资格。因此“9 个轻量桌面”可能比“2 个重负载桌面”流畅，这是工程判断，须实测。
3. **Switchly 展示层**：九格静态信息与低分辨率图占用可控，九路高帧率截图、持续合成和反复 AX 枚举可能显著增加 CPU/GPU、内存与能耗。必须观察 Switchly 和 WindowServer 两边，而非只看应用自己的内存。

不要给出“每个桌面固定多用多少 MB”或“16 GB 必定足够”这类结论。应结合 [Activity Monitor 的 Memory Pressure、Swap Used 与压缩内存](https://support.apple.com/guide/activity-monitor/view-memory-usage-actmntr1004/mac)判断，不能只看剩余空闲内存。

### 4.2 可计算的图片成本

按 RGBA 8-bit 解码图片估算：宽像素 × 高像素 × 4 字节。只计算单份像素，不包含纹理、多缓冲、合成、缓存与临时原图。

| 9 张图片的尺寸 | 单张 | 9 张合计 |
| --- | --- | --- |
| 320×200 px | 约 0.24 MiB | 约 2.20 MiB |
| 640×400 px（320×200 pt 的 2× 图） | 约 0.98 MiB | 约 8.79 MiB |
| 3840×2160 px | 约 31.64 MiB | 约 284.77 MiB |

9 张 4K 图片若每秒更新 10 次，仅单份像素生成量就接近 2.78 GiB/s，尚未计捕获和合成成本；这是量级估算，不是测得的内存带宽。文件压缩很小也不能据此认为解码后占用同样小。若每格展示多个窗口图，应按实际图片总数计算，不能仍按九张估算。

### 4.3 推荐的刷新和缓存策略

- 首帧先显示桌面别名、序号、图标、活动状态和可用的旧缩略图；无图不会阻止选择。窗口归属未可靠建立时不显示猜测的数量或图标。
- 非活动桌面默认用已知窗口的低分辨率图拼合示意，不承诺像 Mission Control 一样实时；标记“缓存预览”，可提供最后更新时间。没有有效缓存显示图标，不主动切过去补拍。
- 切换通知、窗口变更和打开面板时合并更新元数据；截图按当前可见窗口兴趣和既有服务预算调度，不给九格各加一个高频定时器。
- 网格关闭即注销其刷新兴趣；其他已打开面板仍可继续使用自己的兴趣。快速切换、目标销毁或显示器变更时取消过期任务并检查返回结果身份。
- 复用 ThumbnailService 的缓存、去重与并发限制，不新增独立捕获池；分配全局预算，不能因新增网格而把所有额度扩大九倍。
- 不另存完整桌面原图，不改变原有小缩略图 24 小时/64 MB 的磁盘边界；内存另设合理预算，收到压力信号清图保留元数据。具体限额由原型测量决定。
- 默认不在后台持续捕获所有桌面。若以后加入刷新选项，需实测能耗并支持低电量与减少动态效果。

### 4.4 必须做的性能实验

实验方案，尚未执行：同一硬件、相同分辨率/刷新率、相同应用和窗口，分别分布到 1/4/6/9 个桌面。每组先稳定 2 分钟、采样 5 分钟，随机顺序重复至少 3 次；控制窗口总数，才能区分桌面数量与工作负载。

再单独增加窗口总数（9/27/54）和重负载（浏览器视频、IDE 构建、会议屏幕共享），测试 8 GB/16 GB Apple Silicon、可获得的 Intel 机型，覆盖内置屏与外接 4K 双屏。比较：关闭 Switchly、新功能关闭、新功能开启但面板关闭、图标总览、缓存缩略图总览。双屏时分别测独立 Spaces 开/关，并记录 Stage Manager 状态。

记录 Switchly/WindowServer CPU、物理内存占用、内存压力、swap 增长、GPU/能耗、截图次数、主线程卡顿、面板首个可交互帧、输入到实际桌面稳定的 P50/P95，以及 100 次切换/窗口移动的成功率。冷启动/暖缓存分开，连续开关面板 100 次检查对象和任务是否释放。

拟定验收目标（原型后校准，不是现有成绩）：暖缓存面板可交互 P95 ≤150 ms；面板关闭后新增网格捕获为零；固定负载下新增空闲 CPU 平均 ≤1 个百分点（以单核 100% 为口径）；9 格低分辨率总览新增物理内存稳态 ≤40 MiB，连续开关后无持续增长。系统切换耗时以原生直达基线比较并报告，不以 150 ms 面板目标代替。未通过则先退为图标/缓存总览，而不是加更多预热。

## 5. 功能说明

### 5.1 命名与概念

用户可见名称为“桌面网格 / Desktop Grid”。保留现有“工作区 / Workspace”作为应用分组，不自动迁移、不改为原生桌面，不因将应用加入工作区而移动它的窗口。

网格格子绑定一个真实的普通 Space。位置编号用于快捷键，系统桌面编号作为辅助信息，本地别名用于记忆。全屏与 Split View Spaces 单列在“全屏应用”区域，不占用固定九格，避免进出全屏使其他格子跳位。原生桌面顺序和本地网格顺序分别保存，拖动格子只改变本地映射。

### 5.2 总览结构

```text
桌面网格                       显示器：内置屏 ▾    管理桌面…
┌────────────────┬────────────────┬────────────────┐
│ 1 开发 A       │ 2 查资料 A     │ 3 测试 A       │
│ 图标/缓存示意  │ 图标/缓存示意  │ 图标/缓存示意  │
├────────────────┼────────────────┼────────────────┤
│ 4 开发 B       │ 5 写作 ●当前   │ 6 沟通         │
│ 图标/缓存示意  │ 图标/缓存示意  │ 图标/缓存示意  │
├────────────────┼────────────────┼────────────────┤
│ 7 素材         │ 8 个人         │ ＋ 创建桌面…   │
│ 图标/缓存示意  │ 图标/缓存示意  │ 经系统完成     │
└────────────────┴────────────────┴────────────────┘
全屏应用：……                     ↑↓←→ 选择 · 回车切换 · Esc 取消
```

这是信息结构草案，不是已确认视觉稿。实现时复用现有材质、主题、令牌及 visibleFrame 约束；长标题截断并有可访问完整标签。当前、键盘选中、拖放目标三种状态不能只靠颜色区分。

### 5.3 布局与映射规则

- 1–3 桌面默认单行；4 个推荐 2×2；5–6 个推荐 2 行 3 列；7–9 个推荐 3×3。用户开始配置后不因新增一个桌面自动重排旧格，扩容需明确操作。
- 删除绑定桌面后保留空位；新建桌面待用户绑定空位。空位不代表系统已有一个空桌面。空位可显示“绑定已有桌面”与“创建桌面…”操作。
- 超过九个普通桌面时以显式分页呈现，不能隐藏其他桌面；方向键默认不跨页、不跨行环绕。布局从 3×3 缩小前提示如何安置已有绑定，不删除系统桌面。
- 建议引导关闭系统“根据最近使用情况自动重新排列空间”，不擅自修改系统偏好。即使未关闭也必须按身份跟踪，不能只依赖顺序索引。
- 会话内记录显示器标识、Space 身份、类型与顺序。重启、Dock 重启或显示器变化后重新核对；稳定身份不可用时标记“需要重新绑定”，不把别名静默分配给同序号的另一桌面。

## 6. 创建桌面、移动窗口与分配应用

### 6.1 如何创建一个新原生桌面

首版走完整、可解释的系统流程：

1. 在网格空位选“创建桌面…”，解释该操作会进入 Mission Control；尚未创建时不显示成功。
2. 用户用 Control–↑ 或系统提供的方式进入 Mission Control，在顶部 Spaces 栏点“＋”，建立真正的系统桌面。
3. 回到 Switchly 后重新读取该显示器桌面；确认新增结果，选择要绑定的格子并填写本地别名。
4. 用户取消或系统没有新增时保留原状；枚举失败显示“无法确认桌面变化”，允许刷新或手动重新绑定。

若能可靠打开 Mission Control，可提供快捷入口；否则显示步骤，不能靠未验证的坐标点击。创建 9 个桌面不等于创建 9 个应用副本。自动批量补齐到九桌面列为后续可行性研究，不要求用户关闭 SIP。

### 6.2 如何将一个现有窗口移到桌面

原生路径：到窗口所在桌面，打开 Mission Control，将窗口拖到顶部目标桌面；也可拖到屏幕边缘等待进入相邻桌面。[Apple 官方操作说明](https://support.apple.com/guide/mac-help/work-in-multiple-spaces-mh14112/mac)是此流程依据。

Switchly 增强路径（仅对已实测支持的后端开放）：窗口预览的“移动到桌面…”或将预览拖到格子 → 显示目标名称 → 提交移动 → 重新确认窗口归属。默认“移动后留在原桌面”，另提供“移动并跟随”。移动和跟随分别报告结果：窗口已移动但跳转失败时，不把整个操作显示为成功或强行移回。

拖到空位先完成创建/绑定，再由用户确认移动；不得先从界面移除原窗口。拖动期间悬停不自动切换桌面。目标失效、窗口关闭、权限缺失、最小化/全屏窗口不支持等情况取消并给可理解反馈，不无限重试。首版不自动退出全屏或恢复最小化来迁就移动。

### 6.3 “把 app 移到桌面”必须拆成三种动作

| 用户意图 | 交互与语义 | 计划 |
| --- | --- | --- |
| 移动当前窗口 | 只移动选中的那一个窗口，同应用其他窗口不变 | 支持后端验证后开放 |
| 移动此应用现有窗口 | 先展示窗口数量/列表与目标，再逐个执行；未来新窗口不因此自动跟随 | 第二阶段；报告成功、失败、跳过数量，提供失败项重试 |
| 此应用以后在此桌面打开 | 切到目标桌面，Dock 中右键应用 → 选项 → 分配给 → 此桌面 | 首版提供系统指引；这是持续分配，不是一次移动 API 的等价物 |

Dock 的“所有桌面”表示同一应用在多个桌面可见，不是复制进程；“无”取消固定分配。原生分配行为参考 [Apple 的 Assign apps to spaces](https://support.apple.com/guide/mac-help/work-in-multiple-spaces-mh14112/mac)。同一浏览器的不同项目窗口应优先使用单窗口移动，避免应用级分配将它们绑定到一起。

如果后续支持 Switchly 新窗口规则，应由用户明确选择、默认只影响新建普通窗口，不自动搬走既有窗口；声明与 Dock 原生分配、全屏窗口、其他窗口管理器规则的优先关系。应用启动不保证会创建新窗口，也不保证新窗口进入用户期望的 Space，必须观察实际结果。

## 7. 交互清单

以下是产品目标；标为“条件”的操作只有运行态能力检测通过才启用，不能以乐观更新代替系统结果。

| 编号 | 操作/入口 | 行为 | 状态和异常 |
| --- | --- | --- | --- |
| G01 | 菜单栏“桌面网格”或全局快捷键 | 在鼠标所在屏幕打开总览；键盘入口可设置为活动窗口所在屏幕 | 初始选中当前桌面；冲突时要求重新配置快捷键 |
| G02 | 单击格子/选中后回车 | 条件：切换到绑定桌面并确认 | 完成后关闭；失败保留总览与错误，可回到系统操作 |
| G03 | 总览内方向键 | 只移动选择框，回车才切换 | 到边界/空位停止；不执行多次系统动画 |
| G04 | 总览内数字 1–9 | 直接选定并提交对应格子 | 空位解释创建/绑定，不发送未知快捷键 |
| G05 | 全局“向上/下/左/右桌面” | 可选配置，按二维邻接选择目标 | 条件：后端支持；默认不占用 Control–↑/↓，避免与 Mission Control 冲突 |
| G06 | 全局“桌面位置 1–9” | 可选的固定位置直达 | 使用用户配置的无冲突组合，区分本地格号与系统桌面号 |
| G07 | Esc、再次触发打开键、点击外部 | 取消并关闭，不因选择框移动而切换 | 提交前取消无系统副作用；提交后不能承诺撤销系统切换 |
| G08 | 空位“＋” | 绑定已有桌面或进入系统创建指引 | 只有检测到真实桌面才建立有效绑定 |
| G09 | 格子“重命名” | 保存本地别名并更新快捷入口标签 | 不宣称已改 Mission Control 的系统名称 |
| G10 | 整理模式拖动格子 | 调整本地位置映射 | 与拖动窗口明确区分；不重排系统 Space |
| G11 | 窗口“移动到桌面…”/拖放 | 条件：移动所选窗口并确认归属 | 无能力时禁用拖放并给出系统方法，不伪装成功 |
| G12 | “移动并跟随” | 条件：先移动，再切换 | 可显示部分成功；不将应用激活当成窗口聚焦 |
| G13 | 应用图标“移动现有窗口…” | 第二阶段：确认范围后批处理 | 处理中禁止重复提交；展示部分成功与跳过项 |
| G14 | “以后在此桌面打开” | 显示 Dock 分配的系统步骤 | 不混同现有工作区应用列表；规则自动化另行验证 |
| G15 | 删除桌面 | 首版引导系统 Mission Control 删除 | 系统会把窗口移到其他桌面，不关闭应用；重新同步后保留空位 |
| G16 | 显示器选择 | 展示所选屏幕的独立网格 | 首版不提供跨屏移整个 Space；独立 Spaces 关闭时使用共享集合并明确标记 |
| G17 | 全屏应用区域 | 条件：跳转对应全屏 Space | 退出全屏重新同步，不挤占普通桌面的固定格 |
| G18 | 系统外部操作 | 对桌面增删、重排、外屏插拔、手势切换进行同步 | 旧任务取消；映射不确定时要求重新绑定 |
| G19 | 缺少截图权限 | 保留图标与名称，解释缓存不可用 | 不从磁盘加载截图，不阻断具备其他权限的切换 |
| G20 | 缺少 AX/后端能力 | 提示如何授权或使用系统路径 | 分别识别权限、系统不支持与操作失败；不引导关闭 SIP |
| G21 | 设置页 | 开关、布局、快捷键、显示器选择策略、本地别名 | 复用 AppSettings/SettingsService，旧数据默认关闭新功能 |
| G22 | VoiceOver/键盘/减少动态效果 | 朗读位置、别名、当前状态、缓存状态；提供操作菜单 | 所有拖放都有菜单替代，主题与焦点清楚，减少动态效果下不使用大幅位移动画 |

操作状态建议统一为：idle → validating → executing → confirming → succeeded / partiallySucceeded / failed / cancelled。一次仅处理一个切换意图；执行中连续方向输入合并为最新有效目标，避免无界排队。超时不能证明失败前已经完成的系统动作被撤销，确认结果后再呈现最终状态。

## 8. 对 Switchly 当前架构的影响

本次只做调研与说明，不修改现有 Swift 实现。当前证据：

- `Models/Workspace.swift` 保存应用分组、快捷键与排序，不表示原生 Space；`Views/WorkspacesView.swift` 中的 ViewModel 也只编辑这些配置。
- `Services/WindowMonitorService.swift` 的 `getOnScreenWindows()` 使用 `.optionOnScreenOnly`，`getAllWindows()` 额外补充最小化窗口；不能当作覆盖全部 Spaces 的桌面索引。`isOnCurrentSpace` 布尔值不包含 Space 身份，也不能区分多个桌面的成员关系。
- 现有 ThumbnailService 提供按 owner 注册的刷新兴趣、分层缓存及捕获并发限制；新网格应复用这些设施。离屏窗口能否得到新图必须实测，不能用缓存伪装实时。
- 现有 `docs/performance-review-2026-10-20.md` 明确未进行 Instruments 实机采样；其自动化验证不能证明 9 桌面负载已通过。本次未重新运行其中的测试。

建议后续新增职责明确的 `DesktopGridViewModel` 与服务协议，将 Space 枚举/能力检测/系统操作放在 Services，映射与配置放在 Models，面板只展示和传递意图。名称与现有 Workspace 区分是必要的领域边界，不是复制已有应用分组服务。能力按 read/switch/create/moveWindow 等逐项声明，带具体不支持原因，避免一个笼统的“已授权”布尔值。

配置通过现有 SettingsService 保存，兼容旧键及 `decodeIfPresent` 默认值。短期 Space ID、PID 与窗口 ID 不能当作跨重启稳定设置；只持久化可重新核对的绑定信息。日志记录 action、display、source/target 标识及错误，不新增窗口标题等敏感内容。

## 9. 实施阶段与验收

### 阶段 A：可行性原型

在不关闭 SIP 的前提下，针对实际支持的 macOS 版本与 Apple Silicon/Intel 分别建立能力表：枚举普通与全屏 Space；读取窗口归属；切换空桌面；同应用不同窗口跨 Space；最小化/全屏的受限行为；Dock 重启、休眠唤醒、系统自动重排、独立 Spaces 开关与外屏插拔后身份恢复。创建桌面首版用系统引导，无需等待其自动化方案。

每项记录操作前后系统状态与目标身份。不能以命令返回成功、应用激活成功或通知发生作为唯一证据；须核对实际显示桌面、窗口归属与焦点。任何后端特定版本不通过，就禁用对应操作。不同 macOS 版本可以有不同能力，但产品说明必须准确。

### 阶段 B：最小可用版本

交付 2×2/2×3/3×3 网格、稳定本地映射、鼠标/键盘选择与直达、当前桌面提示、系统创建/删除指引、图标与缓存总览、异常状态、双语与可访问性。**桌面身份和空桌面切换必须通过阶段 A，才算本功能可交付。** 窗口拖放仅对验证通过的平台开放；未通过的平台必须明确为“通过系统移动”。

### 阶段 C：窗口整理增强

经过跨桌面与多屏实测后增加窗口移动、移动并跟随、应用现有窗口批处理，再评估新窗口分配。自动创建删除、实时桌面视频、替换原生手势与接管系统动画不作为自然追加项。

验收除构建与单元测试外，需要看过浅/深/系统主题和玻璃开关下的真实界面截图；在实际桌面验证窗口移动、取消、失败回退、多屏边界、全屏与权限降级。性能按第 4.4 节实测并记录结果。功能实现后再更新 README、CHANGELOG、设置文案及必要的隐私说明，避免把候选能力写成已经存在。

## 10. 当前结论的限制

本调研证实了产品先例、具体用户痛点与当前上游实现线索，没有进行用户访谈、市场规模统计、Spaces 原型或 4–9 桌面性能实测。推荐推进阶段 A，同时验证是否优于系统数字直达；不能仅凭九宫格看起来更整齐就判定值得发布，也不能因为缺少公开 API 就直接判定绝对不可做。
