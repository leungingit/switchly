# 桌面网格第二轮评估与最终立项判断

整理日期：2026-10-21；本轮系统实验发生于 2026-10-20。分支：`feat/desktop-grid-feasibility`。承接 [候选功能说明](desktop-grid-research-and-spec.md) 与 [第一轮可行性研究](desktop-grid-feasibility-2026-10-20.md)。

## 1. 结论

**目前不能确认预想计划能“完美实现”，完整功能暂不放行。** 已证实桌面元数据和部分窗口操作具有实现基础；核心的真实桌面直达尚未形成可靠证据链。应保留研究分支，暂不把九宫格 UI、窗口拖放或全系统兼容写成已支持功能。

这不是证明所有实现路线绝对不可能，而是本轮没有得到足以交付的完整后端。若“预想计划”是将系统 Spaces 自身变成二维、改变原生垂直手势与动画，该目标原本就不在可承诺范围内；如果是二维导航层，则仍需通过真实切换这一核心门槛。

决策分开如下：

| 范围 | 判断 |
| --- | --- |
| 本地网格、别名、键盘二维选择、布局映射 | 工程上可实现；未制作完整产品界面 |
| 读取普通 Space、当前值与受控窗口归属 | 本机受控样本取得证据 |
| 旧接口控制其他应用窗口 | 本机测试失败，不能采用为通用后端 |
| Bridged 单窗口与批量窗口成员变更 | 本机跨进程夹具成功，生产及视觉验收仍不足 |
| 普通/空桌面真正直达、移动并跟随 | 核心门槛未通过；不能用 current getter 命中替代 |
| 普通桌面创建、删除、应用未来分配 | 保留系统操作指引；自动化没有获得验收 |
| 真正二维系统桌面、原生垂直手势、任意系统永久兼容 | 不承诺 |

## 2. 执行范围与环境

实验机实际报告 `macOS 27.0.1 (26A434)`、arm64、SIP enabled。两个显示器分别 2、4 个普通 Space，总计 6 个；不能将此样本写成单屏 6/9 桌面实验。

主任务串行进行系统操作，低费 `gpt-6-luna` 任务负责功能矩阵和记录复核。主任务对复核结论再核对原始记录，避免把启动时的空归属误解释为桌面切换导致的可见性变化。

使用独立 Objective-C/AppKit 夹具，不修改 Switchly 应用代码、签名、entitlements、持久化设置或系统快捷键。窗口移动目标限于自建测试窗口；另启一个已核验 bundle ID/PID/窗口所有者的测试进程，区分同进程与跨进程权限行为。

交付证据：

- [脱敏结构化实验记录](research/desktop-grid/control-observations.json)：保留实际观察，不含窗口标题、显示器 UUID、用户应用名或截图。
- [复现夹具与说明](research/desktop-grid/control-fixture/README.md)：编译到临时目录，所有测试通过控制按钮显式触发。
- 原始日志及截图留在 `/tmp/switchly-grid-evaluation/`，没有加入仓库。临时文件可能被系统清理，不作为永久可用链接。

## 3. 窗口归属与生命周期

### 3.1 普通窗口与启动阶段

两个自建普通窗口稳定后均可读到原桌面成员。刚创建时成员列表短暂为空，之后进入正常成员关系；说明窗口展示与系统登记是异步过程，不能将创建时的瞬时空结果当作最终归属。

这只解释了受控窗口的创建阶段，**没有解释第一轮 CG 列表中全部 250 个空归属对象**。不能通过本轮两个测试窗口推定已经构建完整、准确的所有用户窗口索引。生产实现应采用窗口生命周期事件和目标确认，不能用无边界重试掩盖未知原因。

### 3.2 最小化、全屏

- 自建窗口最小化标志变为 true，成员仍为原 Space；恢复后标志 false，成员仍一致。
- 自建窗口进入全屏后新增 type 4 Space，current 与该窗口成员指向它；退出后该临时 Space 消失，窗口成员和 current 回到原普通 Space。
- 普通桌面的 ID、顺序与 UUID 值在该次全屏进出过程中保持一致。因此将全屏区域与固定普通格子分开是合理的模型设计。

未验证 Split View、多个应用的全屏组合、最小化窗口跨桌面移动、关闭/退出中途取消或全部第三方应用行为。全屏状态与结构记录成立，不据此宣称全屏总览 UI 已完成视觉验收。

## 4. 窗口移动：必须区分后端与目标进程

| 实验 | 观察 | 判断 |
| --- | --- | --- |
| 旧 `SLSMoveWindowsToManagedSpace` 移动自身窗口 | 成员由原桌面变为目标；移回后匹配原值 | 同进程样本成员变更成功 |
| 旧接口移动另一个夹具进程的单窗口 | 同屏与跨屏对照均未到目标；另一窗口未变 | 跨进程旧路径不通过 |
| 旧接口批量移动另一个夹具进程的两个窗口 | 两个窗口均仍属原桌面 | 批量旧路径不通过 |
| Bridged operation 移动另一个进程的单窗口 | 第一个窗口成员到目标，第二个仍在原桌面；恢复后都在原桌面 | 跨进程单窗口成员变更通过 |
| Bridged operation 批量移动两个窗口 | 两个窗口成员均到目标；恢复后均回原桌面 | 小样本批量成员变更通过 |

Bridged 路径使用 `SLSBridgedMoveWindowsToManagedSpaceOperation` 与内部异步执行函数；后者需要从系统已加载镜像的 Mach-O 符号表定位。**存在运行成功的证据，但这不是公开 API，也不是低维护成本的稳定接口。**

成员关系返回不是完整视觉/焦点验收。本轮没有完成跨应用普通窗口移动后的实际画面、键盘输入目标、所有应用兼容与部分失败恢复测试。因此可以确认“存在窗口移动实现线索”，不能确认用户预想的拖放、整 app 移动和移动并跟随已全部可交付。

## 5. 桌面切换：未通过完整验收

### 5.1 上游高速度手势路径

按已核验上游方式构造横向手势。在本机试验中，出站约 3.13 秒后仍未观察到目标 current ID，按失败停止。回程因本来就在原值，立即返回匹配；**这个回程不是一次成功切换，不能计为往返成功。**

已有系统相邻桌面快捷键的原生控制通道尝试，以及夹具内 Control–Right 事件尝试，也未观察到 current 值变化。相关快捷键偏好只读检查未发现已配置的 1–9 桌面直达条目；没有擅自修改配置。由于输入通道、系统快捷键和实际桌面焦点存在交互，这些记录不能证明用户手动快捷键在该系统一定无效。

### 5.2 Bridged current-Space 设置路径

运行时检查发现 `SLSBridgedManagedDisplaySetCurrentSpaceOperation`。调用后可读到目标 current ID，并可设置回原值；记录中出现约 464/232 ms、627/320 ms 的往返观测时间。这些时间含轮询等待，**不是实际画面切换延迟**。

原始探针把“连续三次 getter 匹配且动画标志未置位”命名为 `confirmed`。进一步核验发现该命名过度：

1. 到目标 current 值时，原桌面普通测试窗口成员仍是原 Space，却仍被报告为 on-screen / visible。
2. 停留到另一个目标值后，显示器截图没有形成能确认目标场景已替换的清晰对照；截图中的既有应用、前台变化和测试窗口层级也需要控制变量。
3. Mission Control 的实际截图能确认原生 4 桌面总览与创建入口，但没有完成“操作前后目标格高亮、普通窗口呈现、输入焦点”三者同步的完整实验。

因此本轮只认定 **current 管理状态可以变更，真实场景切换尚未验收**。不把结果直接定性为系统必然“只改数字”，也不把它算作导航成功。归档代码已改名为 `getterMatched`，并移除未执行的 100 次自动重复入口。

### 5.3 对原计划的影响

普通与空桌面导航都必须是无需借助某个应用窗口、能独立确认实际目标的行为。当前还没有这样一条完整通过的路径，故普通直达、空桌面直达、上下方向快捷键、移动并跟随均不放行。单纯激活某应用或临时把占位窗口放到空桌面，不应被包装成核心能力已解决。

100 次导航成功率试验因该门槛未通过而未执行；不能发布“100% 成功”“零延迟”等结论。此前 100 次静态枚举一致性仅是读取结果，不是切换试验。

## 6. 映射稳定性与恢复

本轮短暂重启了当前用户的 Dock，确认新进程出现。前后读取的两个显示器 Space ID、顺序、类型与 current 值一致；后续受控快照中的 UUID 值和测试窗口成员也保持一致。普通桌面在一次全屏 Space 增删与一次 Dock 重启中取得了会话内稳定性的证据。

但至少一个普通 Space 的 UUID 字段是空字符串。第一轮探针的 `uuidPresent=true` 只检查“是字符串”，不能等同于“有非空且永久稳定的 UUID”。绑定模型不能只检查字段存在，更不能把 ID/UUID 永久稳定当作前提。

系统重启、休眠唤醒、实际屏幕插拔、独立 Spaces 开关、Stage Manager 开关、系统自动重排和普通桌面增删均未完成受控回归。其中部分需要硬件操作或改变用户工作环境，没有为追求覆盖率强行执行。即使可逐项执行，也无法由单机单构建证明 macOS 12+ / Intel 的全面兼容。

2026-10-21 恢复本任务时重新检查：没有残留 GridProbe / ForeignFixture 测试进程，仍为 2+4 个普通桌面，current 值与实验前一致；未重新执行切换或窗口移动。

## 7. 性能与功能矩阵收敛

没有构建完整网格面板，没有持续捕获 9 路图像，也没有执行单屏 1/4/6/9 固定负载 CPU/GPU/WindowServer/内存实验。由于切换后端尚未通过，先投入全量 UI 和性能采样会测到非目标行为，故按阶段门槛暂停。

现有证据支持“元数据读取便宜、图标式总览值得继续考虑”，不支持“9 桌面性能已达标”。在真实切换和固定负载条件建立前，不计算效率收益，也不拿 getter 观测时间与原生切换速度做比较。

修正后的阶段划分：

| 阶段 | 当前状态 | 进入下一步的条件 |
| --- | --- | --- |
| R1 归属与受控窗口 | 普通/最小化/全屏样本有证据；完整索引未通过 | 窗口索引是预览增强门槛，不再阻断纯图标导航模型 |
| R2 原生导航 | 真实普通/空桌面切换未通过 | 必须取得实际画面、目标与输入路由的闭环，然后才跑连续测试 |
| R3 稳定映射 | 全屏与 Dock 重启两个场景有证据，其余未验 | 不误绑定；身份不确定时重新绑定；维护明确支持表 |
| R4 移动增强 | Bridged 受控成员变更有证据，实际交付未通过 | 单独验收窗口呈现、跟随、焦点、错误与恢复 |
| R5 产品界面 | 未实施 | R2 与 R3 核心门槛通过 |
| R6 性能/发布兼容 | 未实施 | 有正确行为的最小产品和可控测试机器 |

“稳定映射”指能核对身份并拒绝错误绑定，不是保证系统身份永久不变。未来性能矩阵必须分别写清“单屏普通桌面数”与“多屏总数”，不能用两屏 2+4 代替单屏 6。

## 8. 最终建议与验证记录

完整预想功能当前为 **No-Go / 暂不进入完整产品实现**；可以保留已有证据，集中解决真实切换后端，但不继续扩散 UI、缓存和自动规则开发。若后续要求同时覆盖“系统真正二维、纯公开接口、自动增删、所有 macOS 12+、无条件窗口控制”，需重新定义产品范围，不能作为当前分支的交付承诺。

本轮评估已把能测的关键路径做成受控实验，并记录因门槛、设备或环境未执行的项；**评估收束不等于所有功能测试完成**。下一次只值得针对 R2 的真实切换证据推进，而不是继续以 current getter 命中增加看似成功的样本数。

验证：独立夹具以 `clang -Wall -Wextra -Werror` 编译，早期版本实际运行并通过原生控制通道触发；已查看测试界面、显示器和 Mission Control 截图。整理后的归档源码修正指标命名、移除未执行入口及固定临时路径，完成重新编译，未宣称全部系统实验重新运行。本任务未修改应用 Swift 代码，因此未运行 `make build` / `make test-unit`。没有版本、发布或用户设置变更，没有提交或推送。

## 9. R2 闭环切换实验（2026-10-21）

目的：补上 §5 缺失的闭环证据。新探针 [switch-closed-loop-probe.m](research/desktop-grid/control-fixture/switch-closed-loop-probe.m) 在原桌面和目标桌面各放一个独立进程的夹具窗口（目标夹具用已验证的 bridged move 放置），对每次尝试同时记录五个信号：(1) 公开 `NSWorkspaceActiveSpaceDidChangeNotification`；(2) 夹具进程自报 `isOnActiveSpace` 与 occlusion；(3) `CGWindowListCopyWindowInfo(OnScreenOnly)` 中原桌面夹具消失、目标夹具出现；(4) 向前台夹具投递 F19 的输入路由；(5) SkyLight getter（仅辅助，不计成功）。成功要求 1–3 同时成立，且 4 适用时通过。原始结果与判定规则见 [r2-switch-observations.json](research/desktop-grid/r2-switch-observations.json)。

### 9.1 环境与前置条件

同 §2：macOS 27.0.1（26A434）、arm64、SIP 开启；原桌面 Space 7，目标取其相邻或非相邻的普通 Space。本次探针由当前沙箱宿主进程启动，**该进程没有辅助功能权限，也没有合成输入（post-event）权限**，也没有屏幕录制权限，因此未截图。只读检查：符号热键 79–82 为默认启用（无自定义参数），118–126 全部未配置，`workspaces-auto-swoosh` 未设置（系统默认），`mru-spaces` 未设置（系统默认，即自动按最近使用重排）。未修改任何偏好、快捷键或 Dock 配置。

### 9.2 结果

| 路径 | 尝试 | 判定 | 关键证据 |
| --- | --- | --- | --- |
| A 合成 Control–方向键（fn+numpad 标志；HID/会话 tap） | 0 | inconclusive | `CGPreflightPostEventAccess=false`，探针拒绝发送；无法在本宿主评估，不是方法失败 |
| B1 `NSRunningApplication` 激活目标夹具 | 12（6 通过 / 6 失败） | pass，有条件 | 干净桌面 6/6：CG 列表原桌面消失、目标出现 300–340 ms，夹具自报 329–462 ms，公开通知 303–439 ms，整次含 300 ms 稳定复查 655–785 ms；目标夹具为活跃 App 与 key window。输入信号 4 因无 post-event 权限不适用，只有代理证据。受 bridged 操作污染后同一做法 0/6 |
| B2 AX frontmost/AXRaise/AXMain | 0 | inconclusive | `AXIsProcessTrusted=false` |
| C bridged 设置 current Space | 5 | fail | getter 0.1–1 ms 即命中、夹具进程收到通知（10–125 ms），但原桌面夹具仍在 CG 列表且 occlusion 可见；信号 2/3 从未成立 |
| C+B bridged 后立即激活 | 3 | inconclusive | 0/3，但三次都在被污染的桌面上运行，激活本身已失效，结论被混淆；干净状态的 C+B 未取得 |
| D 系统“切换到桌面 N”热键 | 0 | not-tested | 118–126 本来就未启用；不修改偏好 |

### 9.3 关键发现

1. **存在一条闭环通过的真实切换路径：激活目标桌面上有窗口的应用。** 依靠系统“切换到应用时切换到其所在空间”的原生行为，公开通知、夹具自报与 CG 列表三项同时成立，并包含非相邻桌面（Space 54，距当前 2 格）。它只适用于目标桌面非空；空桌面无法这样到达。
2. **bridged `SetCurrentSpace` 不是切换，只是改了管理状态。** 它让 getter 和夹具的 `isOnActiveSpace` 变化，却没有让合成画面跟上；因此 getter 命中不能作为成功，`isOnActiveSpace` 也需要与 CG 列表和 occlusion 联合判断。
3. **bridged 操作有副作用，不宜用于生产或恢复。** 对某个 Space 做过 bridged 设置后，该 Space 持续处于“幽灵”状态：夹具自报 `isOnActiveSpace=NO`，CG 仍把其窗口列为在屏、occlusion 可见，且上面第 1 点的激活不再切换（0/6）。本次实验使 Space 6、54、46 进入该状态，跨进程仍然存在。需要用户自行恢复：先在这些桌面之间手动切换一遍，若原生切换仍异常，再由用户重启 Dock 或重新登录（本任务按约束未重启 Dock）。
4. **非相邻切换可能触发按最近使用重排。** 目标为 54（非相邻）的运行结束后顺序由 `[46,7,6,54]` 变为 `[46,7,54,6]`，ID、数量和 current 不变；相邻目标未重排。与系统默认的“自动重排”一致，但未证明因果，原顺序也尚未恢复（可在 Mission Control 中手动拖回）。映射层必须按 ID 绑定并容忍顺序变化。
5. 探针控制进程始终没有收到工作区通知，只有拥有完整 `NSApplication` 运行循环的夹具进程收到；信号 1 因此由夹具进程满足。

### 9.4 恢复检查

每个运行结束时都重新枚举：夹具进程全部终止，Space 数量、ID 与 current（Space 7）和开始时一致；顺序仅在 §9.3 第 4 点所述运行中变化。重新创建的新窗口落在 Space 7 且 `isOnActiveSpace=YES`，说明当前画面在原桌面。

### 9.5 对 R2 Go/No-Go 的影响

- R2 由“No-Go，无任何通过路径”调整为 **有条件继续**：公开激活路径已有闭环证据，可以作为导航到**非空**桌面的候选后端。
- 仍不放行：空桌面直达、移动并跟随、方向键/热键路径（需要在有辅助功能/合成输入权限的宿主，例如已授权的 Switchly 构建中重跑 A、B2、信号 4 与 D）。
- 明确禁止把 bridged `SetCurrentSpace` 用作导航或恢复手段；bridged 窗口移动此前仅用于夹具放置，其对 Space 状态的影响需要单独验证后才能在产品中使用。

补充发现：

1. **桌面编号是跨显示器的全局编号，且跟随当前顺序。** 显示器 1 占桌面 1–2，显示器 2 占 3–5；Control+N 作用于拥有第 N 个桌面的显示器，与光标和 key window 所在显示器无关。第一次执行时按显示器内编号发键，误把显示器 1 切到了 Space 5；已用 B1 仅将其切回 Space 1，并把这次执行作废（见 JSON 的 `supersededFirstPass`）。另一次按过期编号发键：顺序重排后 Control+5 指向了别的 Space，信号 2/3 失败；改为按键时重算编号后通过（桌面 4）。
2. **输入路由分两种情况。** B1、B2、D 切换到有窗口的桌面后，目标夹具成为前台并收到 F19（每次 target=1、origin=0）。A 在显示器 1 上同样如此，但在显示器 2 和所有空桌面上，前台是别的 App，探针按约束没有向其发送按键。结论：切到空桌面后键盘焦点不在 Switchly 控制的任何窗口里。
3. **空桌面到达证明的方法有效性限制。** 无窗口夹具新建的窗口落在“当前活动显示器”的活动 Space，只在显示器 1 上有效（5 次非空目标验证通过），在显示器 2 上不适用。空桌面结论仅来自显示器 1。

## 11. 手势捕获可行性（R3）

范围：在 macOS 27.0.1（arm64）上，普通进程能否拿到触控板四指原始触点，如何识别八方向，以及与系统四指手势的关系。只读检查，没有修改任何系统偏好、快捷键或 TCC，没有切换桌面。探针见 [gesture-probe.m](research/desktop-grid/control-fixture/gesture-probe.m)，构建见 `build-gesture-probe.sh`。标注：**实测**＝本机运行得到；**推断**＝来自资料或结构推理，未在本机验证。

### 11.1 已验证事实（实测）

1. **私有符号仍在。** `dlopen("/System/Library/PrivateFrameworks/MultitouchSupport.framework/MultitouchSupport")` 成功（框架在 dyld 共享缓存中，磁盘上只有符号链接壳）；`MTDeviceCreateList`、`MTRegisterContactFrameCallback`、`MTUnregisterContactFrameCallback`、`MTDeviceStart`、`MTDeviceStop`、`MTDeviceGetDeviceID`、`MTDeviceIsBuiltIn`、`MTDeviceIsRunning`、`MTDeviceGetFamilyID`、`MTDeviceGetSensorSurfaceDimensions` 全部 `dlsym` 得到。
2. **枚举到 2 个设备：** 内置触控板（family 109，表面 124.8×76.8 mm）与另一个非内置设备（family 128，130×110 mm）。注册（返回 1）与 `MTDeviceStart`（返回 0）均成功，3 秒运行、`SIGINT` 中断后 stop/unregister 干净退出，无崩溃。
3. **回调确实收到原始触点，且此时系统四指手势处于开启状态。** 运行期间读取到的偏好：`TrackpadFourFingerHorizSwipeGesture=2`、`TrackpadFourFingerVertSwipeGesture=2`（内置与蓝牙两个域相同）。一次运行中回调收到约 223 帧单指触点（约 90 Hz，帧间隔约 11 ms，`state=4`，归一化坐标 0…1，y 向上），说明 **系统手势开启并不会让 MultitouchSupport 回调失声**。无触摸时不产生帧（回调不会空转）。注意这次 3 指或 4 指没有被做过，四指帧是否同样完整未验证。
4. **以普通 .app 方式启动（`open -n`，责任进程是探针自己，ad-hoc 签名，未授予任何权限）也能枚举并启动设备，没有权限报错或弹窗**；但该次没有触摸，因此“无任何权限时是否有帧”**未验证**（见 11.3 的 T0）。第 3 项的有帧结果是从终端启动的，终端/其父进程可能已有输入监控。
5. **偏好读取（只读）：**

### 11.2 推断与资料（未在本机验证）

- **公开路径拿不到四指原始触点（推断）。** `NSEvent.addGlobalMonitorForEvents` 的 `.swipe/.magnify/.rotate/.gesture/.beginGesture` 是系统已解释的手势事件，只提供有限的 delta，且三指/四指轻扫在系统占用该手势时不会作为 swipe 投递；`CGEventTap` 可看到 gesture 类型事件，但同样是已解释后的结果，没有手指数与坐标。两者都需要输入监控权限，且无法区分“四指”。本轮没有写探针验证，结论依赖 API 语义，信心中等。
- **无法阻止系统消费四指手势（推断，预期如此）。** 系统手势由 Dock/CoreDock 经内部通道处理，MultitouchSupport 回调只是旁路读取触点，不是拦截点。要阻止只有两种办法：让用户在系统设置里关闭对应手势（等同于修改本轮禁止修改的偏好；需要提示用户，写偏好后通常还要重启 Dock，不建议静默做），或使用不稳定的事件过滤技巧。BetterTouchTool、Jitouch 一类产品的做法也是要求用户先关闭系统同方向手势（资料印象，本轮未重新抓取）。**对策：设计为“要求/引导用户关闭系统四指手势，检测到冲突时提示”，而不是尝试拦截。**
- **与本机状态的冲突面：** 当前开启的是四指横扫（切全屏 App）和四指竖扫（调度中心/应用 Exposé）。八方向里的左右、上下四个方向都会同时触发系统动作；斜向四个方向系统不处理，但手指轨迹带有横向分量时系统可能误触发。因此四指方案要么完整关闭系统四指手势，要么只启用斜向（不实用）。
- **TCC（推断）：** 业界实现（OpenMultitouchSupport、BetterTouchTool）报告该路径不需要辅助功能，但在较新系统上读取触点可能需要“输入监控”。本机的直接证据只有第 11.1 第 3 项（从终端启动有帧）；终端是否已有输入监控未验证。
- **资料与许可：** 触点结构与回调签名来自社区对该私有框架的逆向，常见实现为 Kyome22/OpenMultitouchSupport（MIT）和 mhuusko5/M5MultitouchSupport（MIT 一类宽松许可）。本探针**只按布局事实自行声明结构（96 字节，编译期断言大小）**，未拷贝其源码；这些仓库本轮没有重新抓取，许可应在真正引入前再次确认。

### 11.3 需要用户手测的步骤

### 11.4 八方向识别算法（设计）

- **输入：** 回调帧中 `state` 为 making/touching（3、4）的触点；手指数 `n`，质心 `c = mean(position)` 乘以触控板物理尺寸（宽×高 mm，来自 `MTDeviceGetSensorSurfaceDimensions`）换算成毫米，避免归一化坐标在宽高不等时扭曲角度。
- **会话：** `n ≥ 4`（`--min-fingers`）的第一帧开始会话，记录起点质心；`n` 跌破 4 超过 80 ms（`--dropout-ms`，吸收一两帧触点丢失）或 `n=0` 则结束。多于 4 指（含 5）也算，但会话内最多手指数会记录。
- **触发：** 位移 `|c − c₀| ≥ 12 mm`（`--threshold-mm`）时立即触发一次（“阈值命中即发”，会话内只触发一次）；方向取 `atan2(dy, dx)`，y 向上。**抬起时的最终角度另行输出，用于评估早发与最终的一致性**，如果不一致比例高，改为“抬起时判定”或提高阈值。
- **扇区：** 8 个 45° 扇区，中心为 0°、45°、…、315°，所以斜向是 45° ± 22.5°，轴向是 0° ± 22.5°。实现里有 `diagonalBias` 参数（默认 0）：增大使斜向更宽、轴向更窄。人手滑动水平/垂直更容易“吸附”，建议实测后给斜向 2–5° 偏置，这个数据要用 T4 确定，目前是推断。
- **去抖：** 触发后冷却 350 ms（`--cooldown-ms`）；冷却内不开新会话；一次会话只出一次。
- **建议初值：** 最少手指 4、阈值 12 mm（约内置触控板宽度的 10%），丢指容忍 80 ms，冷却 350 ms。这是起点，需要由 T1/T4 数据校准，未经过真实四指样本验证。
- **识别器与框架解耦：** 输入只是“手指数 + 质心 + 时间戳”，便于以后换成其他来源，并方便写单元测试（给定合成轨迹断言方向）。

### 11.5 端到端延迟估算

| 段 | 数值 | 来源 |
| --- | --- | --- |
| 触点到回调 | 帧间隔约 11 ms（约 90 Hz）；硬件到驱动延迟未知 | 实测帧率；硬件延迟未测 |
| 阈值命中到发出指令（本地） | 单帧内完成，`callbackLocalUs` 字段记录（微秒级，待用户手测数据） | 设计；字段待采集 |
| 达到阈值的手势用时 | `sinceSessionStartMs`，待手测，预期 80–250 ms | 推断 |
| 发出指令到桌面切换完成 | Control+N 约 0.75 s；激活目标桌面 App 约 0.63–0.73 s | §10，实测 |

结论：手势识别部分的本地开销可忽略，端到端体感由“阈值命中前的手势用时 + 约 0.7 s 系统切换动画”决定，识别器本身不是瓶颈。系统动画期间的重复触发要靠冷却和“切换中忽略”状态抑制。

### 11.6 风险

- **私有框架维护：** MultitouchSupport 无公开头文件，结构体布局与回调签名随系统变化的风险长期存在；macOS 12–27 之间我们只在 27.0.1 上实测，需要在 12、13、14、15、26 上各跑一次探针（至少 `--list-only` 与单指帧）。运行时要用 `dlsym` 判空并做降级，禁止链接期依赖。
- **兼容性：** 非内置设备（外接 Magic Trackpad）、未来触控板家族、Intel 与 Apple 芯片都可能在设备枚举和尺寸上有差异。
- **权限：** 输入监控是否必需未定（T0）；站外分发时 Developer ID 签名与公证对此无影响，但每次重新签名会让 TCC 条目失效。
- **系统冲突：** 无法阻止系统四指手势；需要用户手动关闭，且关闭后失去原有的四指全屏切换/调度中心功能，这是产品代价而不仅是技术问题。
- **审核与分发：** 私有 API 使用使 Mac App Store 不可行，已符合“站外分发”前提。

### 11.7 对总体 Go/No-Go 的影响

- 技术可行性（实测）：私有路径在 macOS 27 上可枚举、可注册、系统四指手势开启时仍收到触点，R3 由“未知”提升为 **有条件 Go**。
- 条件：（1）T0 确认权限需求并能在产品里正确引导；（2）T1/T2 证明四指（而非一两指）帧完整、方向识别在真实数据上达标；（3）接受“要求用户关闭系统同方向四指手势”的产品代价，或把手势改为不与系统冲突的组合（例如五指或带修饰键）。
- 若 T1 发现四指帧缺失、或 T2 显示关闭系统手势后用户体验不可接受，则手势入口降级为菜单栏、快捷键与点击九宫格，其余部分不受影响（切换已由 §10 路径支撑）。
- 未被本轮改变：R2 的 Go（限定路径）、bridged SetCurrentSpace 禁用结论。
