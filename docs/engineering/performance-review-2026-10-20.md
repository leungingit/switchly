## 已修正的问题

| 问题 | 原有开销或风险 | 修改 |
| --- | --- | --- |
| 多应用预览与工作区逐应用枚举窗口 | 包含 N 个应用时，每轮重复获取 N 次系统窗口列表 | 每轮只获取一份快照，再按应用筛选；空应用列表不枚举 |
| 窗口筛选重复查询进程信息 | 同一应用的多个窗口重复创建进程查询对象 | 单次筛选按唯一 PID 查询，复用应用标识及名称 |
| 缩略图元数据强引用图片 | NSCache 清理图片后，元数据仍持有图片，阻止内存释放 | 元数据只保存字节数、尺寸和时间，由 NSCache 持有图片 |
| 淘汰后重新写入图片缓存 | 单张图片超过预算时，记账条目先被淘汰，图片随后又进入 NSCache | 在同一把锁内先写缓存、再检查和执行淘汰 |
| 预热资格检查与任务占用分离 | 并发请求可能重复捕获同一个窗口；旧代码忽略任务占用失败 | 在同一把锁内检查缓存、退避及进行中的任务，并占用任务 |
| 超时退避计数存在并发访问 | 后台捕获失败与成功写入可能同时修改计数表 | 将退避计数和冷却时间更新放入同一临界区 |
| 重复启动窗口监控 | 再次启动可能覆盖定时器引用，遗留重复轮询 | 已启动时直接返回 |

筛选保留原有的应用标识与名称匹配、大小写处理和窗口 ownerName 回退。工作区保留应用顺序、窗口排序及缺失应用占位。

## 验证范围与后续测量重点

这些测试验证的是调用次数、对象释放与并发调度约束，不代表整体 CPU、常驻内存或切窗延迟的实测改善百分比。

辅助功能接口仍有同步调用：最小化窗口发现以及 Dock 图标树遍历可能等待其他应用响应。当前修改减少了多应用刷新时的重复枚举，但没有把整个辅助功能查询链迁移到后台。这部分应在窗口较多、Dock 放大、目标应用无响应等实机场景中，用 Time Profiler 和 Hangs 采样确定后续优化优先级。

窗口监控仍保留缩略图预热，鼠标监听仍保留原有轮询频率，以维持预览首帧速度和手势响应。空闲能耗与首帧延迟之间的取舍尚未通过实机采样量化。
