# 插件 API / SDK 能力开放路线与执行计划

> 实施进度（2026-11-02）：用户已授权外迁与本地插件体系实施，已完成项、限制与真实验证见 [实施台账](plugin-externalization-progress.md)。本文保留原规划，不将 R2–R5 的未来能力标为已交付。

> 日期：2026-11-02。状态：发展规划，全部新增接口、权限名、配额及版本标签均为建议，尚未实现或获批。
> 上位方案：[插件体系方案](plugin-ecosystem-plan.md)。本路线细化其 §7/§8，不取代既有实现与 D 系列裁决；本文件编号为 API-P01–API-P06。
> 目标：让外部插件能独立完成数据读取、状态存储、交互展示与受控动作；Agent 能通过 SDK 和能力清单准确开发；宿主能力逐步丰富且权限可解释、可撤销。

## 1. 对标结论：丰富度与权限开放程度分别规划

### 1.1 Raycast：完整工具型 SDK，运行环境开放度高

官方提供原生 UI、偏好、存储、剪贴板、窗口、OAuth、后台刷新及系统工具；安全文档说明扩展运行在 Node 子进程的独立 isolate，而文件、网络等 Node 能力没有进一步沙箱限制。OS 权限与商店审核承担部分边界，不能理解为每种操作都有插件级细粒度授权。

借鉴其类型、组件、工具与生命周期完整度；Switchly 使用 capability broker 逐项提供系统动作，不必先加入 Node 才能丰富 API。

来源：[API 索引](https://developers.raycast.com/llms.txt)、[安全模型](https://developers.raycast.com/information/security)、[窗口 API](https://developers.raycast.com/api-reference/window-management)、[存储](https://developers.raycast.com/api-reference/storage)、[剪贴板](https://developers.raycast.com/api-reference/clipboard)、[后台刷新](https://developers.raycast.com/information/lifecycle/background-refresh)、[OAuth](https://developers.raycast.com/api-reference/oauth)、[AppleScript 工具](https://developers.raycast.com/utilities/functions/runapplescript)。

### 1.2 Magpie：分类型扩展，按扩展点选择权限模型

其公开指南区分 Bun 插件、受限中间件、Agent 适配及页面/面板；Bun 插件有宿主权限，页面通过声明权限读取受限数据，不能直接联网。这说明扩展点可按用途设计不同边界。

借鉴类型化扩展点和受限数据桥；不直接移植其供应商鉴权与宿主特权插件模式。

来源：[插件指南](https://usemagpie.ai/docs/plugins)、[社区仓库](https://github.com/magpie-community/plugins)。以上是官方文档核对，不是本机运行测试，也不代表所有插件类型共用同一沙箱。

### 1.3 对 Switchly 的能力映射

| 能力方向 | 对标启发 | Switchly 当前状态 | 路线目标 |
| --- | --- | --- | --- |
| UI | Raycast 原生组件；Magpie 多扩展点 | Dock 四槽位、组件树与 Scene | 补完整组件、布局/主题上下文，后续加入受控详情面板 |
| 配置与状态 | 偏好、插件独立存储 | toggle/select/number；无公开插件私有 KV | 字符串、分组、校验、私有 KV/缓存与数据迁移 |
| 数据接入 | 事件、供应商/数据桥 | 天气、媒体、授权目录只读，主要靠刷新 | 统一订阅、目录 watch、事件合并和可见期生命周期 |
| 窗口/应用 | 窗口查询、移动和系统工具 | 目标快照；focus 仅有权限声明、未接调用入口 | 先当前目标 focus，再受限查询/调整几何 |
| 文件与剪贴板 | 系统 I/O、复制/粘贴 | 有受限文件读，无公开剪贴板 API | 目录令牌、私有写入；先复制，再按动作授权读取/粘贴 |
| 网络/账户 | 网络、OAuth、凭据存储 | 插件无网络，只有宿主天气例外 | 作为可选产品方向，先裁决政策，再做域名级 broker |
| 后台与自动化 | 可配置后台命令、Hook | 可见期刷新，隐藏 VM/Timer 仍有治理缺口 | 可见期事件优先；后续独立后台任务授权 |
| DevX | 类型、模板、CLI、调试 | 尚无可发布 SDK/CLI | 能力清单、fake、真实 JSC 测试工具与端到端演练 |

不把“对标产品有此能力”直接等价为“Switchly 必须实现”。优先级按三个条件排序：能消除当前耦合、能支持多个实际插件、能复用现有系统服务。

## 2. 能力开放模型

### 2.1 五种授权策略

下列层级只用于设计归类；授权仍按具体 capability、范围和场景判断，不提供一个“信任全部”总开关。

| 层级 | 能力示例 | 默认与授权策略 |
| --- | --- | --- |
| L0 插件内部 | 声明式 UI、插件自身设置、受限 KV/缓存、主题与 locale | 安装后可用，设配额；无其他插件数据访问 |
| L1 目标只读 | 当前预览目标元数据、媒体/天气快照 | manifest 声明，按审核/用户策略授权；标题等另分数据范围 |
| L2 用户触发动作 | 聚焦当前目标、播放、复制插件生成文本、打开 URL | 声明权限 + 可信用户动作凭证 + 目标范围；自动 render 不能执行 |
| L3 持续或敏感读取 | 目录 watch、剪贴板读取、跨应用窗口列表、后台任务 | 显式选择范围/用途；可撤销；后台另授权，不能由只读许可隐含 |
| L4 高影响集成 | 用户目录写入、网络、账户、输入注入、跨应用自动化 | 独立产品裁决与隔离门禁；不作为首期 SDK 默认能力 |

“只读”不等于低敏感：目录、完整窗口标题、剪贴板内容都可能包含隐私。存储也需要与信息来源的敏感度相容，不能把 L0 KV 解释为可无限保存敏感快照。

### 2.2 授权对象必须包含范围

建议授权结构包含：插件 ID、已验证发布者、capability、资源范围、使用场景、授权代次。示例范围：当前预览目标、用户选中的应用集合、目录令牌、单次剪贴板读取、明确 HTTPS origin。

- `matches` 只决定激活匹配，不是窗口/文件访问授权；二者独立核验。
- 区分 supported（宿主实现）、granted（用户允许）、available（当前系统/目标可用）。API 存在不代表当前目标支持。
- 必需权限缺失时不激活相关功能；可选权限缺失时继续提供基础能力。不得因为缺一个可选能力把整个插件隐藏。
- 用户动作凭证由宿主生成，绑定插件、实例、动作、目标及短有效期，不能让 JS 自报 `userInitiated: true`。
- 撤销后重新检查排队调用；对已提交 OS 的操作返回真实结果或“结果未知”，不能宣称一定撤回。自动重试不得重复副作用。
- 同插件不同发布者、同权限不同目录/应用/域名、前台扩为后台，均视为新增授权。

### 2.3 旧插件兼容

当前 ctx 会提供目标应用信息与标题摘要，部分媒体动作在 onAction 中调用但没有新式动作令牌。下一主协议新增范围策略；v1/v2 保留兼容适配，在升级迁移文档中明确差异。不能用新权限名使已安装插件突然全部停用，也不能把旧权限自动扩展为更大范围。

## 3. 拟议 API 能力目录与优先级

下表所有路径/权限名是用于评审的草案，不能直接作为开发 SDK 使用；“现有”只指同类功能已在当前代码中出现，不表示草案签名已存在。

| 优先级 / 阶段 | 拟议模块或权限 | 开放内容 | 主要边界 / 用例 |
| --- | --- | --- | --- |
| P0 / R0 | `capabilities`、`environment`、`errors` | 能力实现矩阵、协议版本、locale、主题、减少动态效果、布局约束、结构化错误 | Agent 可以离线判定接口可用性；窗口内容不随 environment 扩散 |
| P0 / R1 | `settings`、`storage`、`cache` | 设置读取/变化、字符串、分组、字段校验；插件独立 KV、TTL 缓存、配额与清除 | 保存抽卡进度、偏好和会话摘要；不开放宿主全部偏好 |
| P0 / R1 | `lifecycle`、`events`、`timers` | activate、suspend/resume、dispose；取消令牌、受控失效、事件订阅 | 所有句柄进入实例资源容器，隐藏后停止活动 |
| P0 / R1 | `assets`、`ui`、`scene` | 普通插件图片、通用列表/空态/加载/错误态、文本输入、选择器、动作面板 | 原生声明式组件；Scene 复用现有预算；新组件按真实用例逐项实现 |
| P1 / R2 | 现有 `media.*`、`weather.current` | 类型/错误一致，状态变化订阅、数据新鲜度、可用操作查询 | 取消页面按最短间隔刷新全部插件；天气来源入口通用化 |
| P1 / R2 | 现有 `fs.read` + 拟议 `fs.watch` | 目录选择令牌、受限批读、增量变化、退订与合并 | 鲸娘只监视授权会话目录；不允许凭路径跨根读取 |
| P1 / R2 | `window.focus`、`window.read` | 先聚焦当前目标与目标只读状态，再明确授权的窗口列表 | 使用现有 AX/匹配服务；结果必须验证目标，标题读取单独范围化 |
| P1 / R2 | `applications.read/launch` | 限定应用元数据、运行状态、用户触发启动/激活 | 不扫描任意文件、不接受任意命令行，不混淆启动与窗口聚焦 |
| P1 / R2 | `clipboard.writeText`、`links.open`、`feedback` | 用户点击复制文本、打开批准 scheme 的 URL、宿主内反馈 | 不读旧剪贴板；URL 不接受 file/javascript/任意本地协议；反馈限频 |
| P2 / R3 | `window.manage`、`displays.read` | 几何、移动/调整大小/最小化等逐项操作、显示器可用区域 | 用户触发；边界约束与能力探测；不承诺跨 Space 必然成功 |
| P2 / R3 | `clipboard.readText/paste` | 单次读取纯文本、用户确认的目标粘贴 | 读与写分权；不提供历史/监听；敏感内容不记录；取消检查目标 |
| P2 / R3 | `ui.detail`、`commands`、`shortcuts` | 按需详情面板、manifest 动作、用户分配快捷键 | 宿主处理冲突；不注册全局键盘监听；面板关闭清理资源 |
| P2 / R3 | `files.export`、`storage.files` | 用户选定保存位置导出、插件私有目录受限文件写入 | 原子写入/配额；不开放任意 fs.write；不执行导出文件 |
| P3 / R4 | `background.tasks` | 用户单独启用的有限任务、周期、结果/上次运行状态 | 无后台 UI、无输入/剪贴板读取；能源调度、单实例、硬超时 |
| 可选 / R5 | `network.http`、`accounts`、`secrets` | 经批准的 HTTPS origin、OAuth PKCE、受控凭据引用 | 需改变现行隐私边界；不允许插件读宿主或其他插件凭据 |
| 可选 / R5 | `integrations`、数据源贡献点 | 注册标准化快照/事件、受限本地 IPC | 先有两个真实集成再抽象；不默认开放任意端口、socket 或全局总线 |

窗口完整标题、其他应用窗口枚举、任意 app 启动、剪贴板读取均须在实现前同步隐私与用途文案，不能因为它们不联网就默认可用。

### 3.1 初始配额建议

这些是设计起点，应通过基准测量后固定进协议；已有更严格限额继续生效，不能借此次规划扩大现有文件/Scene 预算。

- 私有 KV：每插件总量建议 1 MiB、单值 64 KiB，支持 JSON，写合并与 schemaVersion；敏感运行快照默认不持久化。
- 可再生成缓存：建议 8 MiB/插件并受宿主全局上限控制，TTL/LRU，清除不影响业务正确性；不存截图或凭据。
- 初期 watch：建议每插件最多 4 个根内订阅，事件 250–1000ms 合并；关闭/隐藏/撤权归零。底层需要重扫时沿用已有扫描上限。
- 前台事件队列：合并同键更新，队列有界；数据过期只保留最新，动作不重放。
- 外部动作：必须由用户触发，串行/有界并发，不允许 render 触发一轮自动复制、播放或切窗。
- 后台：初始建议最短 15 分钟、每插件最多一个在途任务、最长 5 秒、独立进程可终止；不承诺准点唤醒。具体预算需测量 macOS 12 与当前系统。

## 4. 六个交付阶段

阶段是依赖关系，不是必须增长六次协议主版本。SDK 先从 0.x 演进；只有破坏现有协议才切下一主版本，稳定 1.0 以验收为准。

### R0：公开契约基线（预计 2–3 工程日）

交付：API 清单、现有实现/缺口矩阵、TypeScript 基础类型、manifest/UI schema、一致性正反例、capability 状态说明与文档生成最小链。

必做：将未注入的 focus/AppleScript 与未接通的普通图片准确标记，统一时间单位/错误；公开 JSC 支持的全局和不支持的 Node/浏览器 API。

验收：Agent 只读 SDK/清单就能正确判断现有三个插件所需能力；planned 不出现在可调用稳定类型中；Swift 与 SDK 对共享样本判定一致。

### R1：独立开发闭环与完整基础层（预计 4–6 工程日）

交付：SDK 0.1 候选、模板、build/validate/test/pack 最小 CLI、fake Context、真实 JSC 契约工具；设置/私有 KV/缓存、资源/错误态、生命周期与动作命名空间。

验收插件：外仓三个现有插件 + 一个不依赖媒体/文件的最小计数插件，验证通用性。私有 KV 重启恢复、清除、超限、版本迁移、跨插件访问拒绝均有测试。隐藏后 Timer/订阅无活动，释放后 VM 无泄漏。

退出门禁：外仓无需宿主源码完成构建与业务测试；宿主消费不可变包；普通图片与真实 Dock 基本操作完成验收。该阶段与上位方案 M1/M2 重叠，不重复计入排期。

### R2：本地上下文与受控动作（预计 5–8 工程日）

交付：SDK 0.2 候选，媒体/天气事件、目录 watch、当前目标 focus、应用元数据、点击复制/打开链接、统一资源范围与动作凭证。

验收插件：会话状态面板、媒体控制、当前窗口工具条；至少两个插件消费同一媒体/天气服务，证明无专属 ID 分支。

退出门禁：目录增量变化、撤权、符号链接变化；媒体空状态与系统拒绝；目标关闭/切换时 focus 失败可解释；复制只能由点击触发。事件模式对比轮询需测 CPU/唤醒/延迟，不提前声明更省电。

### R3：桌面生产力扩展（预计 6–10 工程日）

交付：SDK 0.3 候选，受限窗口操作、显示器上下文、详情面板/动作、用户快捷键、单次剪贴板读取/粘贴、用户选位置导出。

本阶段先拆分窗口、剪贴板、文件三个独立 PR，不一次扩大全部权限；每项须有实际外仓插件场景后才进入 stable。

验收插件：窗口布局助手、复制/粘贴工具、授权目录中的状态列表及导出。多屏/缩放/屏幕边界、AX 拒绝、目标身份变化、快捷键冲突、用户取消导出均需实际验证。

退出门禁：系统作用域与隐私说明已更新；任何“成功”结果有系统查询或明确定义的成功标准。跨 Space 或不可调整窗口只能诚实降级，不把声明存在当作平台能力保证。

### R4：开放插件隔离与有限后台（先做 2–3 日原型，再估完整实现）

交付：受限 helper/IPC、硬超时与崩溃恢复、授权代次、单插件诊断；通过后增加 background.tasks。对不可信插件的隔离是本阶段前置，不能靠勾选“后台权限”替代。

顺序：先验证最小 macOS 12 helper 与沙箱 → 验证不可越权的宿主桥 → 杀死卡死插件不影响主 App → 评估每插件/共享 helper 成本 → 再实现后台调度。

验收：死循环、内存压力、插件崩溃、IPC 伪造/超大消息、插件停用、App 退出、睡眠唤醒；后台不重复重放动作、不绕过前台动作凭证。设置展示上次执行、预算超限和关闭入口。

R4 的隔离基础可提前并行原型，但在此之前只承诺受审核插件路线；未经审核插件不得依据开放目录被自动信任。

### R5：可选在线集成（政策裁决后立项，不承诺日期）

仅当用户希望插件接入在线服务时启动；第一步是批准隐私模型，不能先加 fetch 再补政策。

设计：HTTPS origin 级授权、禁止私网/本机默认访问、重定向逐跳校验、响应字节/时间/并发限额、取消、离线错误、凭据脱敏和退出清除；本地 IPC 是另一种权限，不能混在 network.* 中。DNS 与重定向检查必须绑定实际连接，避免校验与连接目标不一致。

账户：优先 PKCE，宿主受控 Keychain 命名空间；凭据用不可伪造引用绑定请求 origin，插件不读原始 token。SDK 提供清楚的登录/刷新/退出流程，不读取其他 App 的会话文件代替授权。

首次场景只选择一个明确服务验证，例如用户主动连接的在线状态面板；不同时做 AI API、所有 OAuth 提供商和完整插件市场。市场下载网络与插件业务网络独立授权、独立实现。

## 6. 暂不列入默认开放承诺的能力

| 能力 | 原因 | 替代路线 / 重开条件 |
| --- | --- | --- |
| 任意 shell / 任意 AppleScript | 能绕过大多数 API 范围，进程隔离也不自动消除副作用 | 类型化动作、宿主审核模板；没有替代方案的明确用例再单独评审 |
| 任意 fs.write、其他插件存储 | 破坏数据和插件隔离 | 私有目录写入、保存面板导出，后续按范围审批 |
| 全局剪贴板监听/历史 | 高敏感且需常驻收集 | 单次用户触发读取，不顺手建立历史库 |
| 原始截图/屏幕持续采集 | 改变既有缩略图隐私与留存边界 | 宿主内部渲染引用，不给 JS 原图；另有实际用例再评审 |
| 全局键盘监听、任意输入注入 | 可读取或影响其他应用输入 | 用户配置快捷键与明确单次粘贴 |
| 任意 HTML/WebView、原生 dylib/FFI | 新增独立安全与兼容面 | 先补原生声明式详情和组件；不可表达的真实场景再评估 |
| 任意本地 HTTP/MCP/IPC 与插件间调用 | 绕过来源、身份、范围与依赖管理 | 注册的集成桥、固定协议/目标与显式授权 |
| 为“功能丰富”引入完整 AI/账户平台 | 当前没有具体产品需求，增加联网与凭据成本 | R5 的单服务试点通过后另定路线 |

以上是本路线的默认范围，后续可由具体产品需求重新裁决；当前路线本身不修改现行禁令。

## 7. SDK 1.0 的定义与验收

1. 核心 API 至少覆盖 R0–R2，外仓至少三个不同类别插件只依赖公开 SDK 开发；不以 API 数量作为完成标准。
2. 稳定接口有 TypeScript、Schema、宿主实现、错误/权限/预算、示例和互操作测试；任何一环缺失均不能标 stable。
3. 未授权、撤销、系统拒绝、目标失效、取消、预算超限、旧设置迁移都有真实或合成回归，明确区分。
4. Agent 演练：只给公开文档和模板，由独立开发流程完成一个新插件；出现的未知接口、需读宿主源码、私有分支都记录为契约缺口。
5. 运行场景记录系统/机型/构建/插件版本，覆盖 Dock、主题、多窗口、隐藏/释放和重复启停。构建与单测不能代替系统验收。
6. R3/R4/R5 可继续作为可选 feature 演进，无需为了 SDK 1.0 开放网络、后台、凭据或全部系统权限。
